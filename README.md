## Аннотация

Работа посвящена обеспечению корректной обработки webhook-событий при синхронизации данных между CRM-системой и внешним сервисом. На базе готового Python-проекта нужно реализовать обработчик событий изменения статуса сделки: REST API для приёма webhook-запросов, хранение актуального статуса сделки в SQLite, идемпотентность (защиту от повторной обработки одного события) и версионирование событий, не позволяющее устаревшим данным перезаписать актуальные.

## Что будет представлено на презентации топика

- Почему доставка webhook работает по принципу at-least-once и чем опасны дубликаты и нарушение порядка доставки.
- Подходы к идемпотентности (ключ идемпотентности, журнал обработанных событий) и версионированию (условное обновление, optimistic concurrency).
- Демонстрация проблемы на стартовом проекте: прогон сценария, в котором устаревшее событие затирает актуальный статус.
- Структура стартового проекта, контракт API, набор тестовых событий, порядок сдачи и критерии оценивания.

## Описание задания

CRM-системы уведомляют внешние сервисы об изменениях через webhook-запросы. Доставка таких уведомлений обычно работает по принципу **at-least-once**: одно и то же событие может прийти несколько раз, а события могут прийти **не в том порядке**, в котором они возникли (повторы, сетевые задержки, параллельная отправка).

Цель задания — на базе готового проекта на FastAPI реализовать сервис синхронизации статусов сделок, который:

- принимает webhook-события `deal.status_changed` по REST API;
- хранит актуальный статус каждой сделки в SQLite;
- обрабатывает каждое событие **ровно один раз** (идемпотентность по `event_id`);
- **не перезаписывает** актуальные данные устаревшими событиями (версионирование по `version`);
- отклоняет некорректные входные данные.

Стартовый проект уже запускается и проходит часть тестов, но содержит наивную реализацию: он безусловно перезаписывает статус сделки при каждом запросе. Места, требующие доработки, помечены в коде комментариями `TODO`.

Подробные этапы выполнения описаны в [tasks.md](tasks.md), критерии проверки — в [assessment.md](assessment.md), требования к окружению — в [environment.md](environment.md).

## Контракт API

### `POST /webhooks/crm`

Тело запроса:

```json
{
  "event_id": "evt_d1001_v2",
  "event_type": "deal.status_changed",
  "deal_id": "D-1001",
  "status": "qualification",
  "version": 2,
  "occurred_at": "2026-10-01T09:30:00Z"
}
```

| Поле          | Требования                                                                 |
|---------------|----------------------------------------------------------------------------|
| `event_id`    | непустая строка, уникальный идентификатор события                          |
| `event_type`  | только `deal.status_changed`                                               |
| `deal_id`     | непустая строка                                                            |
| `status`      | `new`, `qualification`, `proposal`, `negotiation`, `won`, `lost`           |
| `version`     | целое число ≥ 1; растёт с каждым изменением сделки (возможны пропуски)     |
| `occurred_at` | дата и время в формате ISO 8601                                            |

Лишние поля не допускаются.

Ответы:

| Код | `result`    | Когда                                                                                   |
|-----|-------------|-----------------------------------------------------------------------------------------|
| 200 | `applied`   | событие применено, статус сделки обновлён                                               |
| 200 | `duplicate` | событие с таким `event_id` уже получено ранее (в том числе если тогда оно было `stale`) |
| 200 | `stale`     | новое событие, но `version` не больше текущей версии сделки; данные не изменены         |
| 422 | —           | некорректные входные данные; событие не считается обработанным                          |

Пример ответа: `{"result": "applied", "event_id": "evt_d1001_v2", "deal_id": "D-1001"}`.

Почему `duplicate` и `stale` возвращают 200: для отправителя webhook это сигнал «доставлено, повторять не нужно». Код 4xx/5xx заставил бы CRM повторять отправку.

### `GET /deals/{deal_id}`

Возвращает актуальное состояние сделки: `{"deal_id", "status", "version", "updated_at"}`, где `updated_at` — `occurred_at` последнего применённого события. Если сделка неизвестна — 404.

### `GET /health`

`{"status": "ok"}`.

## Правила обработки события

Сервис обрабатывает каждое входящее событие строго в следующем порядке:

1. **Валидация.** Если тело запроса не соответствует контракту — ответ 422 (стандартный ответ FastAPI). Событие не сохраняется и не считается полученным: CRM может повторить его с тем же `event_id` после исправления.
2. **Проверка дубликата.** Если событие с таким `event_id` уже было получено ранее (с любым результатом — `applied` или `stale`), ответ `duplicate`, данные не меняются.
3. **Проверка версии.** Если сделки ещё нет — она создаётся, ответ `applied`. Если `version` события **строго больше** текущей версии сделки — статус, версия и `updated_at` обновляются, ответ `applied`. Иначе (`version` меньше или равна текущей) — ответ `stale`, данные не меняются.
4. **Фиксация.** Событие записывается как полученное вместе с результатом. Шаги 2–4 выполняются в одной транзакции.

Уточнения:

| Ситуация | Ожидаемое поведение |
|---|---|
| Порядок событий определяется по `version` | `occurred_at` для упорядочивания **не используется**, он только сохраняется в `updated_at` |
| Версии отслеживаются для каждой сделки отдельно | `version` = 5 у сделки A никак не влияет на сделку B |
| Пропуски версий (1 → 3) | допустимы, событие применяется |
| Первое событие сделки имеет `version` > 1 | применяется |
| Переходы между статусами (например, `won` → `new`) | не проверяются: любой статус допустим, если версия новее |
| Тот же `event_id`, но другое содержимое | базовый уровень — `duplicate`; уровень Э — 409 Conflict |
| Повторная доставка ранее устаревшего события | `duplicate` (а не `stale`) |
| Повторная доставка после перезапуска сервиса | `duplicate`: сведения хранятся в SQLite, а не в памяти |

## Быстрый старт

```bash
python3.12 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python -m pytest                    # тесты базового уровня
python -m pytest -m advanced        # тесты дополнительных заданий

uvicorn app.main:app --reload       # запуск сервиса, документация API: http://127.0.0.1:8000/docs
python scripts/send_events.py events/scenarios/03_out_of_order.json   # в соседнем терминале
```

База данных по умолчанию создаётся в `data/deals.db` (путь меняется переменной `DATABASE_PATH`). Чтобы начать демонстрацию с чистого состояния, остановите сервис и удалите этот файл (`rm data/deals.db`). Тесты используют отдельную временную базу и не затрагивают `data/deals.db`.

Если в процессе работы вы изменили схему таблиц, также удалите `data/deals.db`: таблицы создаются только при их отсутствии (`CREATE TABLE IF NOT EXISTS`).

## Формат и сроки сдачи

1. Сделать fork (или копию) этого репозитория и выполнить задание в своём репозитории.
2. Записать видеоролик **до 4 минут** — он является отчётом по работе. Загрузить его на Яндекс/Гугл Диск с доступом по ссылке.
3. Добавить ссылку на видео в начало `README.md` своего репозитория.
4. Отправить эксперту ссылку на репозиторий. В репозитории должны быть исходный код, тесты и история запусков GitHub Actions.

Срок сдачи — в течение периода, объявленного преподавателем (ориентировочно 14–16 дней с момента выбора топика). Эксперт проверяет работу, даёт обратную связь в виде списка замечаний и выставляет буквенную оценку (см. [assessment.md](assessment.md#формат-обратной-связи)).
