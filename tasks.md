# Этапы выполнения задания

Общая трудоёмкость — **не более 10–12 часов** (см. таблицу в [README.md](README.md#трудоёмкость)).

## Базовый уровень (оценки Б и Б+)

### Этап 1. Знакомство с проектом (~0,5 ч)

- Сделать fork репозитория, настроить окружение (см. [environment.md](environment.md)).
- Запустить сервис и тесты. Убедиться, что часть тестов падает, и разобраться почему.
- Прогнать сценарии из `events/scenarios` через `scripts/send_events.py` на исходной реализации и зафиксировать, какие данные оказываются некорректными (пригодится для видео «до/после»).

### Этап 2. Идемпотентность (~1,5 ч)

- Добавить в SQLite хранение сведений об уже полученных событиях (`app/db.py`).
- Повторное событие с тем же `event_id` не должно изменять данные; ответ — `duplicate`.
- Сведения должны храниться в базе данных, а не в памяти процесса: после перезапуска сервиса дубликат по-прежнему распознаётся.

### Этап 3. Версионирование и нарушение порядка доставки (~1,5 ч)

- Событие применяется, только если его `version` больше текущей версии сделки; иначе ответ — `stale`, данные не меняются.
- Первое событие сделки применяется при любой версии; пропуски версий допустимы.
- Устаревшее событие тоже считается полученным: его повторная доставка — `duplicate`.
- Проверка версии, обновление сделки и запись о полученном событии должны выполняться атомарно (в одной транзакции).

### Этап 4. Валидация входных данных (~0,5 ч)

- Добавить ограничения в модель `DealStatusChangedEvent` (`app/schemas.py`) согласно контракту в [README.md](README.md#контракт-api).
- Некорректный запрос получает 422, не изменяет данные и не помечается как обработанный.

### Этап 5. Тестирование и CI (~1 ч)

- Добиться прохождения всех тестов базового уровня: `python -m pytest`.
- Убедиться, что workflow GitHub Actions (`.github/workflows/tests.yml`) в вашем репозитории завершается успешно.
- Для оценки Б+: добавить не менее 2 собственных тестов или сценариев в `events/scenarios` (например, длинная цепочка событий, редкий порядок доставки).

Изменять существующие тесты и файлы в `events/` нельзя — только добавлять новые.

### Этап 6. Видеоотчёт (~1,5 ч)

Отчётом по работе является видеоролик **до 4 минут**. В нём необходимо показать:

1. Запуск тестов на исходной реализации и после доработки.
2. Прогон сценариев `01`–`06` через `scripts/send_events.py` (дубликаты, нарушение порядка) и пример некорректного запроса (422).
3. Кратко — устройство решения: схему таблиц, как распознаются дубликаты и устаревшие события.
4. Для оценки Б+ и выше — как обеспечена атомарность и какие ограничения у решения.
5. Для оценок П и Э — демонстрацию дополнительных заданий.

## Дополнительные задания

### Продвинутый уровень — П (~1,5 ч)

Реализовать проверку подлинности webhook-запросов.

- Если задана переменная окружения `WEBHOOK_SECRET`, каждый запрос к `/webhooks/crm` должен содержать заголовок `X-CRM-Signature: sha256=<hex>`, где `<hex>` — HMAC-SHA256 от **сырого тела запроса** с ключом `WEBHOOK_SECRET`.
- Запрос без подписи или с неверной подписью получает 401 до валидации тела и не изменяет данные.
- Сравнение подписей — в постоянное время (`hmac.compare_digest`).
- Если `WEBHOOK_SECRET` не задан, проверка не выполняется (в учебных целях; в продакшене сервис должен отказываться работать без секрета).

Проверка: `python -m pytest -m advanced tests/advanced/test_signature.py`.

### Экспертный уровень — Э (~2 ч)

Обеспечить корректность при конкурентной доставке и защиту от подмены событий.

- Параллельная доставка одного и того же события (несколько потоков одновременно) — применяется ровно один раз.
- Параллельная доставка множества событий одной сделки в случайном порядке — в итоге сохраняется событие с максимальной версией.
- Повторное использование `event_id` с **другим** содержимым — ответ 409 Conflict, данные не меняются; повторная отправка исходного события — по-прежнему `duplicate`.
- В видео объяснить, какие гонки возможны при наивной реализации и как они устранены.

Проверка: `python -m pytest -m advanced tests/advanced/test_concurrency.py`.

Важно: решение должно опираться на механизмы базы данных (ограничения, транзакции, условные обновления), а не на подгонку под конкретные тесты.
