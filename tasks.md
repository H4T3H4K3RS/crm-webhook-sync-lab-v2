# Этапы выполнения задания

Общая трудоёмкость — **не более 10–12 часов** (см. таблицу в [README.md](README.md#трудоёмкость)).

## Общие правила

- Порядок обработки события и все пограничные случаи описаны в разделе [«Правила обработки события»](README.md#правила-обработки-события) — это и есть точная спецификация.
- **Нельзя изменять:** существующие тесты (`tests/`), файлы в `events/`, контракт API (пути, поля, коды ответов, значения `result`), `pytest.ini`. Можно только добавлять новые файлы.
- **Можно изменять:** любые файлы в `app/` (включая структуру модулей), `requirements.txt` (новые зависимости — только с зафиксированной версией), `scripts/`.
- Хранилище — только SQLite (модуль `sqlite3` стандартной библиотеки или ORM поверх SQLite). Внешние СУБД, Redis и хранение состояния в памяти процесса не допускаются.
- Путь к базе данных берётся только из `app.config.get_database_path()`: тесты подменяют его через `DATABASE_PATH`.

## Базовый уровень (оценки Б и Б+)

### Этап 1. Знакомство с проектом (~0,5 ч)

1. Сделать fork репозитория (кнопка **Fork** на GitHub) и клонировать его.
2. Создать окружение и установить зависимости (см. [environment.md](environment.md)).
3. Запустить `python -m pytest`. На исходной реализации ожидается результат **12 passed, 22 failed** — убедитесь, что у вас так же.
4. Запустить сервис (`uvicorn app.main:app`) и прогнать в соседнем терминале сценарий `events/scenarios/03_out_of_order.json` через `scripts/send_events.py`. Записать экран: этот фрагмент («до доработки») понадобится для видео.

**Результат этапа:** окружение работает, исходное состояние тестов и проблема зафиксированы.

### Этап 2. Идемпотентность (~1,5 ч)

1. В `app/db.py` (функция `init_db`) добавить таблицу полученных событий. Имя и набор столбцов — на ваше усмотрение, но:
   - `event_id` должен быть защищён ограничением `PRIMARY KEY` или `UNIQUE` — уникальность гарантирует база данных, а не проверка в Python;
   - рекомендуется хранить также `deal_id`, `version` и результат обработки (`applied` / `stale`).
2. В `app/service.py` (функция `process_event`) перед изменением данных проверить, получено ли событие ранее; если да — вернуть `"duplicate"` без изменений в таблице `deals`.
3. После обработки записать событие в таблицу полученных событий.

**Результат этапа:** проходит `python -m pytest tests/test_idempotency.py`.

### Этап 3. Версионирование и нарушение порядка доставки (~1,5 ч)

1. В `process_event` применять событие, только если сделки ещё нет или `version` события строго больше текущей; иначе вернуть `"stale"`, не изменяя таблицу `deals`.
2. Устаревшее событие тоже записывать как полученное (иначе его повторная доставка вернёт `stale` вместо `duplicate`).
3. Обеспечить атомарность: проверка дубликата, проверка версии, обновление сделки и запись события — в одной транзакции. Соединение открыто в режиме autocommit (`isolation_level=None`), поэтому транзакцию нужно начать явно (`BEGIN IMMEDIATE`) и завершить `COMMIT` / `ROLLBACK`. Допустимо также условное обновление одним запросом (`INSERT ... ON CONFLICT DO UPDATE ... WHERE excluded.version > deals.version`).

**Результат этапа:** проходят `tests/test_ordering.py` и `tests/test_scenarios.py`.

### Этап 4. Валидация входных данных (~0,5 ч)

1. В `app/schemas.py` добавить ограничения в модель `DealStatusChangedEvent` согласно [контракту](README.md#контракт-api): `Literal` для `event_type`, `DealStatus` для `status`, `Field(min_length=1)` для строк, `Field(ge=1)` для `version`, `model_config = ConfigDict(extra="forbid")`.
2. Убедиться, что некорректный запрос отклоняется **до** обращения к базе данных и не попадает в таблицу полученных событий.
3. Строка, содержащая число (например, `"version": "2"`), может как приниматься, так и отклоняться — на ваше усмотрение (строгий режим Pydantic `strict=True` — плюс, но не требование).

**Результат этапа:** проходит `tests/test_validation.py`, ответ на некорректный запрос — 422.

### Этап 5. Тестирование и CI (~1 ч)

1. Добиться прохождения **всех** тестов базового уровня: `python -m pytest` → `34 passed`.
2. Сделать push в свой fork и убедиться, что workflow **tests** в GitHub Actions завершился успешно (шаг «Базовый уровень» — зелёный). Шаг «Дополнительные задания» сборку не блокирует.
3. Для оценки Б+: добавить не менее 2 собственных проверок одним из способов:
   - новый сценарий `events/scenarios/07_<название>.json` в том же формате, что и существующие (он автоматически подхватится `tests/test_scenarios.py`);
   - новый файл тестов `tests/test_custom.py`.

   Проверки должны покрывать ситуации, которых нет в исходном наборе (например, длинная цепочка из 10+ событий в случайном порядке, переход `won` → `new` с более новой версией, повторная доставка всей цепочки событий после её полной обработки).

**Результат этапа:** локально и в GitHub Actions все тесты базового уровня проходят.

### Этап 6. Видеоотчёт (~1,5 ч)

Отчётом по работе является видеоролик **не длиннее 4:00** — запись экрана с голосовыми комментариями. Терминал и код должны быть читаемыми (крупный шрифт).

Рекомендуемый план:

| Время | Содержание |
|---|---|
| 0:00–0:30 | Проблема: прогон сценария `03` на исходной реализации (фрагмент из этапа 1) |
| 0:30–1:30 | Решение: схема таблиц, как распознаются дубликаты и устаревшие события, где начинается и завершается транзакция |
| 1:30–3:00 | Демонстрация на чистой базе: сценарии `01`–`06` через `scripts/send_events.py` (все строки `[OK]`) и один некорректный запрос из `events/invalid` (например, через `/docs`) с ответом 422 |
| 3:00–4:00 | `python -m pytest` (все тесты зелёные), успешный запуск в GitHub Actions; для Б+ — собственные проверки и ограничения решения; для П/Э — дополнительные задания |

Видео загрузить на Яндекс Диск или Google Drive с доступом «все, у кого есть ссылка» (без запроса доступа).

## Дополнительные задания

### Продвинутый уровень — П (~1,5 ч)

Реализовать проверку подлинности webhook-запросов.

- Если задана переменная окружения `WEBHOOK_SECRET`, каждый запрос к `/webhooks/crm` должен содержать заголовок `X-CRM-Signature: sha256=<hex>`, где `<hex>` — HMAC-SHA256 от **сырого тела запроса** с ключом `WEBHOOK_SECRET`.
- Запрос без подписи или с неверной подписью получает 401 до валидации тела и не изменяет данные.
- Сравнение подписей — в постоянное время (`hmac.compare_digest`).
- Если `WEBHOOK_SECRET` не задан, проверка не выполняется (в учебных целях; в продакшене сервис должен отказываться работать без секрета).

Проверка: `python -m pytest -m advanced tests/advanced/test_signature.py`.

### Экспертный уровень — Э (~2 ч)

Обеспечить корректность при конкурентной доставке и защиту от подмены событий.

- Параллельная доставка одного и того же события (несколько потоков одновременно) — применяется ровно один раз.
- Параллельная доставка множества событий одной сделки в случайном порядке — в итоге сохраняется событие с максимальной версией.
- Повторное использование `event_id` с **другим** содержимым — ответ 409 Conflict, данные не меняются; повторная отправка исходного события — по-прежнему `duplicate`.
- В видео объяснить, какие гонки возможны при наивной реализации и как они устранены.

Проверка: `python -m pytest -m advanced tests/advanced/test_concurrency.py`.

Важно: решение должно опираться на механизмы базы данных (ограничения, транзакции, условные обновления), а не на подгонку под конкретные тесты.
